# Requirement coverage: ข้อ 4.5 ทะเบียนผู้เช่า สัญญา และการเงิน

## 4.5.1 ทะเบียนผู้เช่า

| ประเภท | ข้อมูลที่จัดเก็บ |
|---|---|
| นักศึกษา | ชื่อ ที่อยู่ รหัสนักศึกษา เลขบัตรประชาชน คณะ หลักสูตร สาขาวิชา โทรศัพท์ e-mail LINE ID และข้อมูลติดต่อผู้ปกครอง |
| บุคลากร | ชื่อ ที่อยู่ หน่วยงาน เลขบัตรประชาชน ช่องทางติดต่อ และบุคคลติดต่อฉุกเฉิน |
| บุคคลภายนอก | ข้อมูลบุคคล/หน่วยงาน ช่องทางติดต่อ บุคคลติดต่อฉุกเฉิน และไฟล์หนังสือรับรองบริษัท |

`GET /api/tenants` รวมเลขอาคาร ห้อง เตียง เลขที่สัญญา วันเริ่ม วันสิ้นสุด และสถานะเอกสารปัจจุบันในทะเบียนเดียวกัน

## 4.5.2 การจัดทำสัญญา

| ข้อ | การพัฒนา |
|---|---|
| 4.5.2.1–2 | `GET /api/contracts/missing` และหน้า “ยังไม่มีสัญญา” พร้อมสั่งพิมพ์จากหน้าเว็บ |
| 4.5.2.3 | `POST /api/contracts` เก็บวันที่ทำสัญญา ผู้เช่า ห้อง อาคาร ค่าเช่าล่วงหน้า และระยะเวลาเช่าขั้นต่ำ |
| 4.5.2.4–5 | `POST /api/contracts/:id/send` สร้าง System Notification และส่ง e-mail ผ่าน SMTP เมื่อกำหนดค่า |
| 4.5.2.6 | สร้าง PDF ภาษาไทยและเก็บใน `contract_documents` พร้อม SHA-256 |
| 4.5.2.7 | `GET /api/contracts/pending-signatures` แสดงสัญญาที่ส่งแล้วแต่ยังไม่ลงนาม |

## 4.5.3 การต่อสัญญาและสัญญาอิเล็กทรอนิกส์

หน้าเจ้าหน้าที่ “การจองและสัญญา” มีแท็บใกล้หมดอายุสำหรับสร้างฉบับต่อสัญญา ส่งลงนาม เปิด PDF และตรวจ Timeline ย้อนหลัง ส่วน Portal “การเช่าของฉัน” ให้ผู้เช่าตรวจ PDF และยืนยันด้วยรหัสผ่านได้โดยตรง

ฉบับต่อสัญญาใช้สถานะ `renewal_pending` ระหว่างรอลงนาม สัญญาเดิมจึงยังมีผลอยู่ เมื่อผู้เช่าลงนามสำเร็จ ระบบจึงเปลี่ยนฉบับใหม่เป็น `active` และฉบับเดิมเป็น `expired` ภายใน transaction เดียว

- `GET /api/contracts/alerts` ใช้เกณฑ์รายเดือนตรวจตั้งแต่วันที่ 25, รายภาคการศึกษาล่วงหน้า 30 วัน และรายปีล่วงหน้า 60 วัน
- `POST /api/contracts/:id/renew` สร้างสัญญาฉบับใหม่แบบ versioned และเชื่อม `previous_lease_id`
- การลงนามฉบับต่อสัญญาใช้ flow ส่งและลงนามเดียวกับสัญญาใหม่
- `POST /api/contracts/:id/sign` อนุญาตเฉพาะบัญชี Portal ที่ผูกกับผู้เช่าในสัญญา และต้องยืนยันรหัสผ่านอีกครั้ง
- เมื่อลงนามสำเร็จ ระบบสร้างใบแจ้งหนี้ที่ผูกกับสัญญาภายใน transaction เดียวกัน โดยสัญญาใหม่คิดค่าเช่าล่วงหน้าและเงินประกันแรกเข้า ส่วนฉบับต่อสัญญาคิดเฉพาะค่าเช่าล่วงหน้าเพื่อไม่เรียกเก็บเงินประกันซ้ำ
- หลักฐานประกอบด้วย user ID, username, วิธีพิสูจน์ตัวตน, IP, user agent, timestamp, UUID หลักฐาน, hash ก่อนลงนาม และ hash ฉบับลงนาม
- `GET /api/contracts/:id/history` เรียกดูเหตุการณ์ย้อนหลังแบบ append-only
- สัญญาที่ลงนามแล้วแก้ไขผ่าน API ไม่ได้ การต่อสัญญาต้องสร้าง version ใหม่
- PDF ฉบับลงนามเก็บแยกจากฉบับส่งลงนาม และส่งกลับพร้อม header `X-Document-SHA256`

## E-mail และระบบภายนอก

ตั้งค่า `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM` และ `PORTAL_BASE_URL` เพื่อส่ง e-mail จริง หากยังไม่ตั้งค่า รายการจะอยู่ใน outbox สถานะ `queued` โดยไม่ทำให้การแจ้งเตือนในระบบสูญหาย

## 4.5.4 ใบแจ้งหนี้

| ข้อ | การพัฒนา |
|---|---|
| 4.5.4.1 | `POST /api/invoices` ตั้งหนี้รายบุคคล หรือสร้างอัตโนมัติเมื่อลงนามสัญญา พร้อมเลขใบแจ้งหนี้และการป้องกันรายการซ้ำ |
| 4.5.4.2 | `POST /api/invoices/:id/send` ส่งผ่าน SMTP หรือบันทึกสถานะ `queued` เมื่อยังไม่ตั้งค่า |
| 4.5.4.3 | Portal แสดงเฉพาะใบแจ้งหนี้ของผู้เช่าที่ผูกกับบัญชี |
| 4.5.4.4 | `GET /api/invoices/:id/document` สร้าง PDF ภาษาไทยสำหรับดาวน์โหลด |

## 4.5.5 ใบเสร็จรับเงิน

- `POST /api/payment-proofs` ให้ผู้เช่าแนบ JPG, PNG หรือ PDF พร้อมยอด วันเวลา และเลขอ้างอิง
- `POST /api/payment-proofs/:id/review` ให้ผู้มีสิทธิ์ตรวจหลักฐาน อนุมัติหรือปฏิเสธพร้อมหมายเหตุ การอนุมัติจะสร้าง Payment และ Receipt ใน transaction เดียวกัน
- Portal แสดงเฉพาะใบเสร็จของผู้เช่า และ `GET /api/receipts/:id/document` ใช้ดาวน์โหลด PDF
- การยกเลิกใบแจ้งหนี้และใบเสร็จบังคับระบุเหตุผลและบันทึก Audit Log

## 4.5.6 ข้อความหลังเข้าสู่ระบบ

- เจ้าหน้าที่กำหนดประเภทข้อความ ผู้รับทุกห้อง/เฉพาะห้อง รายการอ้างอิง และวันเวลาหมดอายุได้
- `GET /api/announcements` กรองข้อความหมดอายุออกอัตโนมัติสำหรับบัญชีผู้เช่า
- Portal แสดงข้อความที่ Landing Page หลัง Login ผู้เช่ากดหัวข้อเพื่ออ่านรายละเอียดและเปิดสัญญา ใบแจ้งหนี้ หรือใบเสร็จที่เกี่ยวข้องได้

## 4.5.7 การลาออกจากหอพัก

- ผู้เช่ายื่น `POST /api/checkout-requests` ได้เฉพาะสัญญาและเตียงของตนเอง และมีคำขอที่กำลังดำเนินการได้หนึ่งรายการ
- เจ้าหน้าที่ดำเนินการตามลำดับ `submitted → debt_checked → inspected → approved` เพื่อป้องกันการข้ามการตรวจหนี้หรือห้อง
- ขั้นตรวจห้องเก็บเลขมิเตอร์น้ำ/ไฟวันย้ายออก รายการเสียหาย และสร้างใบแจ้งหนี้รอบสุดท้ายอัตโนมัติ
- ระบบไม่อนุมัติหากยังมีใบแจ้งหนี้คงเหลือ เมื่ออนุมัติจะสิ้นสุดสัญญา ปล่อยเตียง และตั้งห้องเป็น “ไม่พร้อม” รอตรวจรับ

## 4.5.8 การคืนเงินประกัน

- ยอดคืนคำนวณจากเงินประกันตามสัญญาหักความเสียหาย และออกหนี้เพิ่มเฉพาะส่วนเสียหายที่เกินเงินประกัน
- เจ้าหน้าที่บันทึกเลขอ้างอิง วันเวลา และแนบ JPG/PNG/PDF ของหลักฐานโอนคืนผ่าน `POST /api/checkouts/:id/refund-transfer`
- ผู้เช่าดูรายการหัก ยอดคงเหลือ วันโอน และหลักฐานได้เฉพาะรายการของตน ระบบสร้างการแจ้งเตือนทั้ง System และ e-mail พร้อม Audit Log

## 4.5.9 การแจ้งซ่อม

- รองรับการแจ้งโดยเจ้าหน้าที่และผู้เช่า โดย Portal บังคับขอบเขตข้อมูลตามบัญชีผู้เช่า
- ทุกครั้งที่เจ้าหน้าที่อัปเดตสถานะหรือผลซ่อม ระบบสร้าง System Notification และส่ง e-mail เมื่อ SMTP พร้อมใช้งาน

## 4.7 การรับเงินและนำส่งเงิน

- รองรับเงินสด เงินโอน ไฟล์ธนาคาร และบัญชีออนไลน์ โดยเก็บเลขอ้างอิงและผู้รับเงิน
- `POST /api/remittances` สรุปใบเสร็จรายวัน แยกรายได้มหาวิทยาลัย เงินประกัน เงินสด และเงินโอน
- Workflow การนำส่งคือ `draft → submitted → approved` พร้อมผู้ดำเนินการและ timestamp ทุกขั้น
- ขั้นอนุมัติบังคับเลขอ้างอิงการโอนตามยอดแต่ละประเภท และเลขที่ใบเสร็จรับเงินเล่มมหาวิทยาลัย
- `POST /api/remittances/:id/cancel` ยกเลิกได้โดยต้องระบุเหตุผลชัดเจนและเก็บประวัติ
- บัญชีพัก บัญชีมหาวิทยาลัย และบัญชีเงินประกันอ่านจาก Environment เท่านั้น API ส่งเลขบัญชีแบบปกปิดเพื่อไม่ให้ข้อมูลจริงหลุดใน repository

## ขอบเขตด้านกฎหมาย

ระบบวางหลักฐานตามแนวทางของกฎหมายธุรกรรมทางอิเล็กทรอนิกส์และคำแนะนำเรื่อง e-Signature ของ ETDA ได้แก่ การระบุตัวผู้ลงนาม การแสดงเจตนา การเก็บวันเวลา และการตรวจความครบถ้วนของเอกสารด้วย hash อย่างไรก็ตาม การรับรอง compliance ขั้นสุดท้ายต้องให้ฝ่ายกฎหมายของมหาวิทยาลัยตรวจแบบสัญญา วิธีพิสูจน์ตัวตน ระยะเวลาเก็บข้อมูล และนโยบายพยานหลักฐานก่อนใช้งานจริง
